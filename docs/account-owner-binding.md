# 계좌 소유자 바인딩 설계

이 문서는 #775의 검토안이다. 현재 구현은 가장 작은 사용자 ID를 계좌 소유자로 판단한다. 계좌 소유권을 명시적으로 기록하면 계정 삭제 후 남은 계정의 순서가 바뀌어도 권한이 이전되지 않는다.

## 보존할 범위

- 계좌를 실제로 관리하는 기존 사용자를 확인해 첫 바인딩을 설정한다. 계좌·체결 및 계좌 파생 기록을 볼 수 있는 기존 소유자의 접근을 유지한다.
- 검증된 공유 분석의 로그인 사용자 접근과 공개 시장 알림을 유지한다. 계좌 참조 기록과 공유 증명이 없는 레거시 기록은 계좌 소유권이 확인된 범위에서만 제공한다. 레거시 행에 대한 실제 영향 규모는 확인 전까지 미정으로 둔다.
- #833의 소유자 미확인 알림 차단을 유지한다. 제출자 기록과 일반 분석 공유는 계좌 소유자 등록의 근거로 사용하지 않는다.

## 명시적 바인딩과 복구

`0027`에서 추가한 단일 바인딩 행은 사용자 FK와 서버 생성 바인딩 세대를 가진다. FK는 nullable이고 사용자 삭제 시 `ON DELETE SET NULL`을 적용한다. 새 제품 정책에서는 FK가 비어 있는 동안 소유자 전용 조회·변경·발송을 닫는다. 계정 생성, 가장 작은 ID, 이름이나 숫자 ID의 재사용은 바인딩을 만들지 않는다.

설정은 계좌를 관리할 권한이 확인된 운영자의 승인된 로컬 절차에서만 한다. 의도한 사용자와 현재 비어 있는 바인딩의 세대를 확인한 뒤 단일 조건부 쓰기로 저장하며 새 세대를 발급한다. 이미 채워진 바인딩이나 오래된 확인 결과로 덮어쓰려는 시도는 거절한다.

| 상황 | 동작 |
| --- | --- |
| 최초 설정 | 기존 계좌 관리 권한을 확인한 사용자를 명시적으로 연결한다. 현 DB의 계정 순서로 소급하지 않는다. |
| 같은 계정의 인증 수단 복구 | 계정과 바인딩을 보존한다. 기존 세션을 폐기하고 인증 수단을 다시 발급한다. |
| 소유자 계정 삭제 | 바인딩 행은 남고 사용자 참조가 비워진다. 다른 계정의 기존 세션으로 계좌 권한을 얻을 수 없다. |
| 삭제 후 계좌 소유자 복구 | 동일 계정 주체와 바인딩을 보존한 검증된 백업, 또는 승인된 로컬 복구 절차로만 복원한다. 다시 열기 전에 세대를 새로 발급하고 이전 권한을 무효화한다. |
| 다른 주체를 새로 연결 | 계좌 관리 근거를 다시 확인한다. 과거 제한 기록은 별도의 동일 계좌·기록 귀속 증거와 승인이 있을 때만 제공한다. |

## 제품 연결과 되돌림

승인된 운영자는 `python -m desk.cli account-owner-status`로 빈 슬롯과 세대를 확인한다. 계좌 관리 권한과 기존 계정 ID를 별도로 검증한 뒤 `python -m desk.cli bind-account-owner --user-id <ID> --generation <세대> --confirm`을 실행한다. 실패하면 슬롯과 계정을 다시 확인하고, 이전 세대로 재시도하지 않는다. 두 명령은 이미 적용된 스키마를 요구한다. 바인딩 저장은 읽기 보호나 과거 기록 권한을 전환하지 않는다.

1. `0027`의 바인딩과 `0028`의 제출자 스키마, 로컬 설정 도구를 준비한다. 보호 정책을 전환하기 전에 계좌 관리자를 검증한다.
2. 포트폴리오 REST·SSE, 체결, 계좌 참조 분석, 보유 감시, 알림 타임라인·푸시, 알림 채널에서 같은 바인딩을 확인한다. 열린 SSE는 각 배치에서 현재 세션과 바인딩 세대를 확인한다. 대기 중인 발송과 사용자별 캐시는 세대가 바뀌면 무효화한다.
3. 비어 있는 바인딩을 공개 수신자와 구분한다. #833의 미발송 기록 규칙을 유지하고 지연된 알림도 발송 전에 소유권을 재검증한다. 제한된 분석과 파생 집계는 기록의 귀속을 확인하고, 공유 분석과 공개 시장 알림은 기존 범위를 유지한다.
4. 운영 전 레거시 가시성, 열린 스트림, 알림 및 캐시 영향을 확인한다. 권한 문제가 생기면 소유자 전용 표면을 닫고 바인딩을 보존한다. 백업 복구 뒤에도 이전대로 접속을 열기 전에 세션을 폐기하고 바인딩 세대를 새로 발급한다.

보안 리뷰에서는 권한 설정·삭제·복구와 오래된 세션·스트림·대기 발송을 본다. 최종 리뷰에서는 기존 소유자와 공유 분석의 호환성, 데이터 보존 및 배포 순서를 본다. 이 검토안의 합성 SQLite 테스트는 명시 바인딩, FK 삭제 및 같은 ID 재삽입, 복구 세대, 공유 유지 정책을 시험한다. 제품 스키마와 실제 PostgreSQL 실행은 후속 검증 범위다.
