# 차트 봉·롱숏·장중 수급 응답 시간 (#859)

[캘린더·선 감시·모의 손익 측정](secondary-api-latency.md)의 냉/온 p95는 각각
52.060/43.906ms, 49.256/55.013ms, 93.709/56.411ms이고 동시 health는 44.956/24.159ms였다.
이번에는 별도 시장 요청 묶음으로 세 경로와 동시 health를 측정한다.

## 재현

`backend`에서 프로젝트 의존성을 설치한 Python으로 실행한다.

```sh
python -B -m tests.market_read_latency_benchmark --samples 30 --bundles 4 --origin-ms 50
```

- 한 창에서 인증된 `/api/candles`(QQQ 일봉 130개, RSI·스토캐스틱), `/api/longshort`(BTC·ETH·SOL 계약),
  `/api/market/flow/intraday`(고정 날짜, 5분)를 각 4번 동시에 요청한다. 한 창당 health 프로브는
  제출 25ms 후 예정된 시점부터 HTTP 응답까지 잰다. 예약 시각 이후의 이벤트 루프 대기도 포함하며
  실제 제출 시 다른 요청이 남아 있었던 창 수를 별도로 센다.
- Yahoo 봉 읽기와 바이낸스 통계 HTTP 응답에 각각 50ms의 합성 지연을 적용한다.
  바이낸스 계약 해석은 고정 매핑이다. SQLite에는 같은 시각과 값의 21 거래일 분봉 스냅샷 8,841행을 삽입한다.
  조회·행 변환·밴드 계산·API 직렬화는 실제로 실행한다. 외부 연결 및 호스트 환경 설정을 차단한다.
- 냉 창에서는 앱의 봉·롱숏 통계·프로그램 밴드 캐시만 비운다. SQLite 페이지·연결 풀과 프로세스는 유지한다.
  온 창에서는 같은 요청을 바로 반복한다. 인증 및 스냅샷 적재는 계측 전에 끝낸다. 초기 창의 최대 응답은
  따로 출력하며 p95에는 넣지 않는다. p95는 표본을 정렬해 95% 순위를 올림한 값이다.
- 이전 리비전은 별도 워크트리의 `backend`에서 실행한다. 피검증 리비전의 `backend`를 `PYTHONPATH`로 주고,
  이 PR의 `backend/tests/market_read_latency_benchmark.py`를 절대 경로로 실행하면 하네스와 입력이 같다.

## 해석과 남은 확인

장중 수급은 냉 창에서 같은 KST 거래일의 과거 20일을 요청마다 읽고 밴드를 반복 계산했다. 변경 후에는
날짜와 스냅샷 원천마다 한 스레드가 읽고 계산하며 후속 요청은 결과를 받는다. 다른 날짜나 원천은 독립적으로
계산할 수 있다. 조회 예외와 취소를 공유한 뒤 다음 요청에서 재시도할 수 있다. 온 창에도 최신 당일 스냅샷
조회와 차트 응답 가공은 요청마다 수행한다.

로컬 값은 Windows의 인프로세스 ASGI, SQLite, 합성 원천에서 나온 값이다. 실제 증권·시세 원천 지연,
PostgreSQL 왕복 시간, 네트워크와 운영 중인 다른 수집 작업의 경합은 이 측정에 포함되지 않는다.
수정 후 예비 반복의 냉 창 health p95는 89.415ms로 실행 간 변동이 있었다. 장중 수급 이외 경로의
작은 시간 차이는 개선 효과로 해석하지 않는다.
배포 후 24시간 운영 slow request 관측은 별도 완료 조건이다.
