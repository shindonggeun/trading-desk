# 시장 스트림 지연 검증 (#690)

이 절차는 같은 합성 시세·수급을 실제 브라우저의 시세판과 시장 수급 패널에 넣고 REST 폴링과 SSE의 DOM 반영 시간을 비교한다. 합성 원천, 수집기 지연, REST 응답과 SSE 프레임은 모두 루프백 픽스처가 만든다. 백엔드의 Redis, 브로커 원천, 운영 인그레스는 아래의 별도 운영 검증 대상이다.

## 로컬 재현

프론트 의존성을 설치한 체크아웃에서 저장소 루트 기준으로 실행한다.

```text
git rev-parse HEAD
node frontend/benchmarks/market-stream-latency.mjs
```

1. 출력된 루프백 URL을 브라우저의 새 프로필이나 비공개 탭에서 열고 **측정 시작**을 누른다. 같은 서버 주소에서 측정은 한 탭만 실행하고 종료까지 탭을 전경에 둔다.
2. 도구는 폴링 → SSE → SSE → 폴링 순서로 실행한다. 회차마다 새 브라우저 문서에서 두 패널의 초기 REST 응답을 받은 뒤 측정을 시작한다. SSE 회차는 두 채널이 준비될 때까지 기다린다. 폴링 회차에서는 같은 SSE 경로가 503을 반환한다.
3. 회차마다 동일한 종목·시장과 같은 원천 이벤트 일정, 같은 40 ms 합성 수집 지연을 쓴다. 초기 값은 제외하고 채널별 세 표본을 매칭한다. 기본 모드는 시세 15초·수급 30초의 프론트 폴링 간격을 그대로 사용하며 몇 분이 걸린다.
4. 출력 JSON을 작업 기록에 붙인다. 체크아웃 SHA, 실행 모드, 브라우저, 각 채널의 표본 수와 REST 요청 수를 함께 기록한다. 표본 누락, 시각 역전, 전송 모드와 일치하지 않는 REST 요청 수가 나오면 도구가 해당 측정을 실패로 표시한다.

동작 점검은 아래 짧은 절차로 실행한다. `--quick`은 프론트 폴링 및 원천 이벤트 간격을 0.06배로 줄인다. 같은 모드 안에서만 비교한다.

```text
node frontend/benchmarks/market-stream-latency.mjs --quick
```

## 결과 읽기

| 출력 | 계측 기준 |
| --- | --- |
| `sourceAt` | 합성 원천이 새 표본을 생성한 시각. SSE의 `source_at` |
| `observedAt` | 같은 표본을 픽스처가 받아 REST와 SSE에서 모두 조회 가능해진 시각. SSE의 `observed_at` |
| `domAt` | 실제 패널의 숫자가 해당 표본 값으로 바뀐 것을 `MutationObserver`가 처음 확인한 시각 |
| `rest` | 준비 단계 이후 측정 회차에서 시세판·수급 패널이 보낸 REST 요청 수 |

세 시각은 같은 호스트의 Unix 밀리초 시계를 사용한다. JSON에는 회차별 원시 표본과 모드·채널별 원천→수신, 수신→DOM, 원천→DOM의 p50·p95가 포함된다. 분위수는 올림 순위로 계산하며 이 절차의 모드·채널별 표본은 6개라 p95는 관측 최댓값이다. DOM 반영은 화면의 값이 바뀐 시점이며 실제 화면 출력 장치의 표시 시각과 차이가 있을 수 있다.

## 장중 운영 실측

운영 화면 한 탭에서 폴링("전")과 스트림("후")을 같은 값 · 같은 시각에 함께 잰다. 서버 설정은 바꾸지 않는다 —
그 탭만 폴링으로 그리고, 스트림은 비교용으로 받기만 한다.

### 무엇을 재나

계측은 `frontend/src/marketLatency.ts`. 평소에는 꺼져 있고 `localStorage["desk.marketStream"]` 이 켠다(새로고침 뒤 적용).

| 값 | 뜻 |
| --- | --- |
| `"poll"` | 화면은 폴링으로만 그린다(이름표 "폴링"). 스트림은 연결해 받기만 한다. `rest` 와 `sse` 를 함께 잰다 |
| `"measure"` | 화면은 지금처럼 스트림으로 그린다. `sse` 만 잰다 |

| 구간 | 어디서 | 뜻 |
| --- | --- | --- |
| 후: 관측 → 화면(스트림) | `report().channels.<채널>.sse.observed` | 스트림 메시지의 `observed_at`(ms) → 그 메시지가 패널 값을 바꿀 수 있게 닿은 때(스트림만으로 이어 간 값 기준 — 화면이 맞춤 REST 로 이미 같은 값이어도 센다). **장중 1~2초 판정 값** |
| 전: 관측 → 화면(폴링) | `report().channels.<채널>.rest.observed` | 폴링이 화면에 가져온 값이, 그 요청 전에 스트림이 마지막으로 받아 둔 값(시세는 가격, 수급 · 선물은 `fetched_at`)과 같을 때 그 `observed_at` 부터. 폴링 대기가 그대로 들어간다 |
| 원천 → 화면 | 같은 자리의 `.source` | 원천이 시각을 줄 때만(수급) |
| 원천 → 관측 | 서버 `GET /api/status` → `market_stream.source_lag_sec` | collector 의 읽기 주기와 원천 발행 주기가 정한다. 전송과 무관 |
| 관측 → api 송출 | 서버 `market_stream.lag_sec` | 버스(프로세스 안 · Redis) 구간 |

- 스트림 쪽은 메시지가 바꾼 키만 센다. 재접속 스냅숏(`ready` 전)은 전송 지연이 아니라 세지 않는다. 채널이 `degraded` 여도
  연결이 살아 있으면 센다 — 그 시간은 기록할 때 따로 적는다.
- 스트림만으로 이어 가는 값은 처음 받은 REST 값에서 시작한다. 그때 추정 칸이던 종목은 그 화면을 다시 열 때까지 스트림 표본이 없다(`unmatched` 로 보인다).
- 폴링 쪽은 키의 첫 값(기준선)과 같은 값의 반복을 세지 않는다. 짝이 없는 값은 `unmatched`, 그 요청을 보낸 뒤에야 스트림에
  나타난 값은 `self`(폴링이 직접 읽어 발행한 값 — 스트림만 쓰는 화면에는 없을 갱신)로 세고 표본에서 뺀다. 시세는 버스가
  종목당 초당 1번으로 합치므로 중간 가격은 `unmatched` 가 될 수 있다.
- 페인트가 아니라 데이터가 패널 상태에 닿은 시각이다. 합성 측정(위)에서 수신 → DOM 은 수 ms 였다.
- 시계: `skew()` 가 `/api/status` 의 `now`(ms)를 7번 읽어 왕복이 가장 짧은 표본으로 서버 − 브라우저 차이를 정하고 보정한다.
  오차는 ±`skew_rtt_ms`/2. 보정 전 값은 `observed_raw`.
- 데스크의 관측 시각이 원천의 실제 변화보다 늦은 만큼(collector 주기)은 두 경로에 똑같이 들어가 비교에서 빠진다. 그 구간은 `source_lag_sec` · `.source` 로 따로 본다.

### 절차

1. 배포된 SHA 가 이 계측을 포함하는지 확인한다(`~/deploy/trading-desk/src/REVISION`). 정규장(평일 09:00~15:30 KST) 중에 한다.
2. 로그인한 브라우저(Playwright 컨텍스트 하나)에서 콘솔로 `localStorage.setItem("desk.marketStream", "poll")` 을 정하고, 탭(페이지) 두 개를 연다.
   같은 출처라 값은 두 탭이 함께 쓴다. 계측은 탭마다 따로다.
   - **시세(quote)**: Live 화면의 시세판(`QuoteBoard`). 정규장 국내 종목(한투 틱)이 있어야 한다. 브로커 폴링 시세(한투 틱 없음)는
     폴링이 직접 읽은 값이라 거의 모두 `self` 가 되어 "전" 표본이 없다. 대시보드의 즐겨찾기 시세는 재지 않는다.
   - **수급(flow) · 선물(futures)**: 대시보드의 시장 수급 패널. 한 번에 하나만 그리므로 시장 선택(코스피 · 코스닥 ↔ 선물)을 바꿔 차례로 잰다.
   - 이름표가 "폴링" 이면 된다. 창을 앞에 둔다(가려진 탭은 폴링을 쉬고 스트림도 닫는다).
3. 탭마다 `await __deskMarketLatency.skew()` → `__deskMarketLatency.reset()`.
4. 20~30분(수급 · 선물은 각각) 둔 뒤 탭마다 `JSON.stringify(__deskMarketLatency.report())` 를 받고, 같은 때 `GET /api/status` 의 `market_stream` 을 받는다.
5. 끝나면 `localStorage.removeItem("desk.marketStream")` → 새로고침. 스트림으로 그리는 실제 화면을 확인하고 싶으면
   `"measure"` 로 한 번 더 잰다(`sse` 만).

### 기록

이슈 댓글에 SHA, 시간대(KST), 브라우저, 서버 역할(`role` · `market_stream.mode`), `skew_ms` · `skew_rtt_ms`, 아래 표를 남긴다.

| 채널 | 전: rest.observed p50 / p95 (n · unmatched · self) | 후: sse.observed p50 / p95 (n) | 원천→관측 p50 / p95 (서버) | 관측→송출 p95 (서버) |
| --- | ---: | ---: | ---: | ---: |
| quote | | | | |
| flow | | | | |
| futures | | | | |

- 판정: 시세 · 수급의 `sse.observed.p95` 가 2초 이하면 목표 충족. 원천 → 관측은 전송과 무관한 수집 주기라 따로 적는다.
- 표본이 10개 미만인 칸, `degraded` 가 뜬 시간, `skew_rtt_ms` 가 큰(예: 200 ms 넘는) 경우는 그대로 적고 판정에서 뺀다.
- 운영 Redis · 인그레스가 끊긴 조건의 채널별 폴링 복귀는 별도 결과로 기록한다(#854 는 CI 의 실제 Redis 로 확인).
