# 화면 API 공유 캐시 리허설 (#689)

대시보드 지수 요약, 차트, 시장판에서 쓰는 요청을 합성 시세로 재생한다. 각 요청 묶음의 응답 시간과 원천 호출을 기록해 프로세스 로컬 캐시와 Redis 공유 경로의 효과를 확인할 수 있다. 수급 카드와 선물 수급의 비교는 [#844 도구](../backend/tests/flow_cache_benchmark.py)에서 실행한다.

## 실행

백엔드 개발 의존성이 설치된 격리 워크트리에서 실행한다.

```powershell
cd backend
.venv/Scripts/python -m tests.screen_cache_benchmark --samples 30 --upstream-ms 20 --redis-ms 1
.venv/Scripts/python -m pytest -q tests/test_screen_cache_benchmark.py
```

임시 SQLite와 합성 계정으로 로그인한 뒤 인프로세스 ASGI 요청을 보낸다. 원천은 합성 Yahoo 봉을 반환하며, Redis 비교에는 짧은 지연을 넣은 메모리 대역을 사용한다. 공유 캐시를 활성화한 경우 앱의 직렬화, 캐시 키, TTL과 조회·저장 경로를 유지한다. 결과에는 브라우저 렌더링, 실제 Redis 왕복, 운영 브로커 요청 시간이 포함되지 않는다.

## 요청과 캐시 상태

| 묶음 | 대표 요청 | 확인하는 공유 경계 |
| --- | --- | --- |
| 대시보드 첫 지수 요약 | `/api/candles`로 `^KS11`, `^KQ11`, `NQ=F`의 일봉 5개씩 조회 | 휴대폰 요약에 쓰이는 L1 전용 요청 |
| 차트 | QQQ의 `/api/candles`(RSI·스토캐스틱 포함)와 `/api/oscillator` | 봉과 오실레이터 계산 결과의 캐시 동작을 함께 확인 |
| 시장판 | `NQ=F`, `ES=F`, `^KS11`, `^KQ11`의 `/api/batch/candles`와 `/api/batch/levels` | 타일의 L1 전용 봉과 공유 가능한 지지·저항을 묶어서 확인 |

각 묶음을 Redis 비활성·활성에 대해 세 상태로 실행한다.

- `cold`는 매 표본마다 API 로컬 캐시와 공유 캐시가 비어 있다.
- `peer_warm`은 별도의 프로세스가 먼저 같은 응답 경로를 요청한 상황을 재현한다. 매 표본의 준비 요청 뒤 API 로컬 캐시를 비우고 공유 캐시를 남긴다.
- `api_warm`은 API가 같은 HTTP 요청 묶음을 한 번 처리한 상태에서 재요청한다.

p50과 p95는 요청 묶음 전체의 완료 시간이다. 앱 시작과 로그인은 측정 전에 끝낸다. 시장판의 두 API를 동시에 호출하므로 브라우저가 첫 지지·저항 호출에 적용하는 2.5초 대기 시간은 포함하지 않는다. `api_origin_by_method`와 `redis_calls_by_method`는 준비 요청을 제외한 원천과 Redis 호출 수다. `redis_stats`는 같은 표본 구간의 적중·미적중·저장 등 캐시 통계다. p95는 정렬한 표본에서 `ceil(0.95 × n)`번째 값이다.

## 결과 해석

Redis 활성 `peer_warm`과 Redis 비활성 `peer_warm`을 비교해 다른 API 프로세스에서 재사용한 효과를 확인한다. 캐시 적중이 생겨도 같은 묶음의 L1 전용 캔들은 계속 원천을 호출할 수 있으므로, 묶음 p95와 함께 메서드별 원천 호출을 확인한다. `api_warm`은 기존 API 프로세스의 재요청 비용을 비교하는 기준이다.

### 측정 예시

Windows에서 표본 30개, 합성 원천 지연 20ms, 합성 Redis 지연 1ms로 실행한 `peer_warm` 결과다.

| 묶음 | p95 비활성 → 활성 (ms) | 원천 호출 비활성 → 활성 | Redis 적중 (활성) |
| --- | ---: | ---: | ---: |
| 대시보드 첫 지수 요약 | 39.165 → 42.883 | 90 → 90 | 0 |
| 차트 | 45.282 → 29.797 | 60 → 30 | 30 |
| 시장판 | 80.078 → 56.194 | 360 → 360 | 120 |

차트의 공유 오실레이터는 표본당 원천 호출 하나를 줄였다. 시장판은 지지·저항을 공유했지만 로컬 갭 계산이 일봉·주봉을 읽어 원천 호출 수는 같았다. 모든 `api_warm` 사례의 원천 호출과 Redis 왕복은 0이었다. 실행 환경과 스케줄링에 따라 지연 수치는 달라진다.

운영의 p95 100ms 목표와 브로커 호출 수는 실제 트래픽과 실제 Redis가 포함된 별도 운영 측정으로 검증한다.
