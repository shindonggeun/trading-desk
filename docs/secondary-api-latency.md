# 캘린더·선 감시·모의 손익 응답 시간 (#859)

#863은 차트·시세 요청이 몰리는 동안 캘린더·선 감시·모의 손익과 health의 최대 응답 시간을 측정했다.
#858의 후속 PR은 시세 요청의 전역 동시 상한을 도입하고 batch·추정가와 auth/me를 측정했다.
여기서는 캘린더·선 감시·모의 손익과 동시 health의 합성 p95를 별도로 측정한다. [PR #863](https://github.com/shindonggeun/trading-desk/pull/863), [PR #873](https://github.com/shindonggeun/trading-desk/pull/873)

## 재현

`backend`에서 프로젝트 의존성을 설치한 Python으로 실행한다.

```sh
python -m tests.secondary_api_latency_benchmark --samples 30 --bundles 4 --fx-ms 50
```

- 실제 FastAPI 앱의 인증과 ASGI 핸들러를 사용한다. 임시 SQLite에 종료 거래 120건과 선 감시 신호 60건을 넣고
  관심 티커의 실적과 경제 일정을 합성한다. 냉 상태에서 환율 조회에 50ms 지연을 주며 외부 연결은 차단한다.
- 냉 상태는 캘린더의 로컬 달력 캐시와 모의 손익의 환율·계산 캐시를 비운 상태다. 로그인과 픽스처 삽입은 측정 전에
  마치며, SQLite 페이지 캐시와 연결 풀은 초기화하지 않는다. 온 상태는 바로 뒤에 같은 요청을 다시 보낸 결과다.
- 선 감시는 응답 캐시가 없어 두 상태에서 모두 설정과 최근 신호를 DB에서 읽는다. 캘린더의 외부 경제 일정과
  실적 수집은 요청 시 조회하지 않는다.
- 목표는 경로별 p95 500ms 이하와 동시 health p95 100ms 이하다. p95는 정렬한 표본에서 95% 순위의 값을
  올림한 순위 값을 가져오는 방식으로 계산한다. 한 창에서 세 API를 각 4회와 health를 1회 제출한다.
  같은 제출 시각으로부터 응답까지를 재므로 태스크가 실행되기 전 대기도 포함한다.

## 측정 결과

Windows, Python 3.13.5, BLAS 1스레드에서 위 명령을 실행했다. 냉·온 각각 30창으로 세 API는 경로별
120표본, 동시 health는 30표본이다.

| 요청 | 냉 p95(ms) | 온 p95(ms) | 목표(ms) |
|------|-----------:|-----------:|---------:|
| `GET /api/calendar` | 52.060 | 43.906 | 500 |
| `GET /api/notify/line-watch` | 49.256 | 55.013 | 500 |
| `GET /api/paper/summary` | 93.709 | 56.411 | 500 |
| `GET /api/health` | 44.956 | 24.159 | 100 |

세 API와 health가 냉·온 목표를 모두 통과했다. 모의 손익의 재계산과 환율 조회는 냉 창마다 각 1회,
온 창에서는 0회였다. 달력 로컬 캐시 미스는 냉 215회, 온 0회였다.

처음 요청하는 세션에서는 라이브러리와 워커 초기화도 일어난다. 준비 창의 요청은 `initial_window_max_ms`에
별도로 내고 반복 냉·온 p95에서 제외한다. 위 실행의 준비 창에서 캘린더 최대는 229.030ms였다.
재시작 뒤 첫 요청의 p95나 지속 부하에서의 반복 health는 이 값으로 판정할 수 없다.

이 측정에는 실서비스 인그레스, 실제 원천, 운영 Postgres, 장 시작의 차트·시세 혼합 부하가 포함되지 않는다.
#859의 배포 후 24시간 운영 기준은 운영 로그에서 확인한다.
